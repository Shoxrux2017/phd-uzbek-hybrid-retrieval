## 1. Главный вывод для research gap (предложение, CURRENT_GAP не менялся)

- **Ни одна из 41 работы не закрывает ядро v0.8 refined.** Ни в одной нет связки: *несколько морфологических вариантов лексического канала (raw/stem/lemma) × один фиксированный dense-ретривер D → overlap / уникально найденные релевантные документы / oracle union → инкрементальный прирост гибрида → признаки запросов*. Предложение: **gap v0.8 не менять**.
- **Сильно занято (подтверждено многократно):** сравнение raw vs stem vs lemma (root, n-gram, truncation) в лексическом поиске для морфологически богатых языков — финский, шведский, немецкий, русский, чешский/болгарский, турецкий, монгольский, амхарский, урду, хинди/гуджарати, эстонский, непальский. Результат устойчиво «нормализация помогает, но какой вариант лучше — зависит от языка, модели ранжирования и запроса»; простая усечка (prefix-5) почти всегда конкурентна.
- **Современные работы, где рядом стоят лексика с морфологией и dense-модели** (ближе всего к gap): CR000100 Silver Retriever (польский: BM25 word vs lemma + собственный dense-ретривер и 7 других нейросетевых моделей на одних test sets), CR000073 MILQA (венгерский: BM25 raw vs lemma + embedding-модели), CR000914 (польский: стратегия выбора леммы меняет NDCG и глубокий recall BM25), CR000448 (корейский: морфологический токенизатор BM25 + 11 dense + «ансамбль» без метрик), CR000149 (амхарский). **Но нигде нет разложения взаимодополняемости** и нигде морфологические варианты не сопоставлены с одним фиксированным D.
- **Ближайшие «сигналы» в пользу нашей гипотезы (без проверки в нашей постановке):** CR002216 Turunen — объединение двух морфологических представлений (morphs + lemmas) превосходит каждое, особенно на коротких запросах с OOV (взаимодополняемость *внутри* лексического канала); CR002210 Fidan — смешение raw и stemmed выдачи; CR000179 GliLem — авторы прямо **предполагают**, что лемматизация полезна для глубокого recall кандидатов в гибридных системах, но не проверяют; CR000566/CR000504/CR000491/CR000161/CR000529 — эффект смены лексического представления разный для разных запросов (per-query win/loss).
- **Уточнение формулировок gap (предложение):** можно добавить в список «что литература уже не позволяет утверждать» пункты: «query-dependent (per-query) выбор/взвешивание морфологического варианта — новая идея» (занято: Paik 2013) и «комбинация двух морфологических лексических представлений — новая идея» (занято: Turunen 2012, Fidan 2012).

## 2. Выводы для дизайна эксперимента (сводно по карточкам, предложения)

1. **Конфигурация BM25 фиксируется и публикуется полностью** (токенизатор, апострофы o‘/g‘, регистр, стоп-слова, стеммер/лемматизатор, k1/b) — почти во всех работах она NOT_REPORTED, что делает результаты несравнимыми.
2. **Правило выбора леммы при неоднозначности и fallback для OOV** — часть условия `BM25_lemma` (Pacanowska: только правило выбора дало +4.09 NDCG@10; Ozturkmenoglu: shortest vs longest lemma — MAP 0.11 vs 0.35).
3. **Дополнительные контроли:** prefix-n усечка и, по возможности, gold-лемматизация как верхняя граница (Khaltar & Fujii, Can, McNamee).
4. **Qrels pool строить из всех каналов, включая D** — пулы только из лексических систем занижают dense (Silver Retriever footnote 9, CURE, 2AIRTC).
5. **D не обучать на hard negatives, добытых тем же BM25** — иначе D не независим (Silver Retriever).
6. **Отдельные dev/test;** выбор чекпойнтов, α фьюжна и параметров стеммеров — только на dev (Sahu & Pal и Mekonnen подбирали на тесте).
7. **Статистика:** per-query paired тесты + bootstrap CI; большинство работ либо без тестов, либо с неясной процедурой.
8. **Признаки запроса:** длина запроса (надёжно модифицирует эффект нормализации), OOV/имена собственные, compound-подобные формы, вариативность написания, fertility под токенизатором D.
9. **Опциональные дешёвые пилоты на открытых данных** до появления узбекских: MILQA (венгерский), 2AIRTC (амхарский), амхарский news-benchmark.

## 4. Предлагаемые исправления флагов full-text triage

Флаг `carries_complementarity_evidence = YES` при triage ставился за любой per-query/разбивочный анализ. После полного чтения верификаторы/авторы карточек предлагают уточнить (решение за исследователем):

- **CR001352**: Triage flag carries_complementarity_evidence=YES re-assessed: only cluster-level recall crossover between black-box system groups, no relevant-set overlap/unique hits/oracle union/fusion.
- **CR001735**: Triage flag carries_complementarity_evidence = YES should arguably be NO: single system, no lexical-semantic channel comparison
- **CR002114**: Triage flag carries_complementarity_evidence=YES proposed to be downgraded to 'indirect (per-topic RF variability)'
- **CR000491**: Triage flag carries_complementarity_evidence=YES is too strong: only qualitative lexical-vs-lexical per-topic AP variation; propose recoding to partial
- **CR000490**: Triage flag carries_complementarity_evidence=YES is too strong: only lexical-vs-lexical per-topic AP deviation; propose recoding to partial
- **CR000338**: Triage flag carries_complementarity_evidence=YES overstates: Table 9 is per-topic AP of the word-based run across languages only; propose recoding to NO/partial
- **CR002158**: propose carries_complementarity_evidence YES → NO (stratified mean bpref, not lexical–semantic complementarity).
- **CR000688**: No BM25 (LM with fixed lambda = 0.5 only), no lemmatization, no dense retrieval, no fusion, no per-query/overlap/unique-hit analysis; triage flag carries_complementarity_evidence = NO confirmed
- **CR000161**: Triage flag carries_complementarity_evidence=YES should be read as stem-vs-raw per-query AP change within lexical retrieval only
- **CR000935**: Triage flag carries_complementarity_evidence=YES should be read as per-query stem-vs-raw precision differences within lexical retrieval only
- **CR002024**: Triage flag carries_complementarity_evidence=YES should be read as qualitative per-query failure attribution within a lexical pipeline only
- **CR000561**: Triage flag carries_complementarity_evidence=YES should be read as qualitative lexical-vs-lexical per-topic variation only

Общая рекомендация: различать `YES (lexical–dense)` и `partial (lexical-vs-lexical per-query)`; во всех 40 работах lexical–dense взаимодополняемость на уровне запросов/документов не измерена.
